Custom Metrics Autoscaler on OpenShift Local

This page walks through starting OpenShift Local (CRC), enabling cluster monitoring, installing the Custom Metrics Autoscaler operator, and creating the workshop namespace. All four workshop steps depend on this setup being complete.

Prerequisites

  • OpenShift Local (CRC) 2.30+ installed and licensed

  • oc CLI in your PATH

  • git CLI in your PATH

  • A host machine with at least 16 GB of RAM (CRC will use 14 GB)

  • A host machine with at least 6 CPU cores (CRC will use 6)

1. Configure and start CRC

~5 minutes (CRC first start downloads a ~3 GB bundle)

What: Set CRC memory and CPU limits, then start the cluster.

Why: The default CRC configuration (9 GB RAM, 4 CPUs) does not leave enough headroom for the OpenShift monitoring stack. Cluster monitoring alone needs 4-6 GB on top of the base cluster.

crc config set memory 14336
crc config set cpus 6
crc start
INFO Checking if running as non-root
INFO Checking if crc-admin-helper executable is cached
...
INFO Starting OpenShift cluster... [waiting 3m]
INFO
INFO To access the cluster, first set up your environment by following 'crc oc-env' instructions.
INFO Then you can access it by running 'oc login -u developer https://api.crc.testing:6443'.
INFO To login as an admin, run 'oc login -u kubeadmin https://api.crc.testing:6443'.
INFO
INFO You can now run 'crc console' and use these credentials to access the OpenShift web console.
The kubeadmin password is printed in the crc start output. Copy it into your myenv.sh file before proceeding.
These steps were validated on CRC with 14336 MB RAM and 6 CPUs (crc config set memory 14336 && crc config set cpus 6). If the CRC API server becomes unresponsive (TLS handshake timeout errors), wait 60 seconds and retry. Run crc status to confirm the VM is still Running. If the VM has stopped, run crc start again. The CRC API can time out briefly when the VM is under memory pressure or after a period of idle.
Example 1. Verify: CRC is running
crc status
CRC VM:          Running
OpenShift:       Running (v4.21.14)
RAM Usage:       ...
Disk Usage:      ...
Cache Usage:     ...

2. Log in and rename the context

What: Authenticate to the CRC cluster and rename the auto-generated context to crc.

Why: OpenShift generates a long context name such as default/api-crc-testing:6443/kubeadmin. Renaming it to crc keeps every oc command in this workshop consistent.

Create a file called myenv.sh in the workshop root (it is gitignored) and fill in the kubeadmin password from the crc start output:

export CRC_API_URL="https://api.crc.testing:6443"
export CRC_PASSWORD="<kubeadmin-password>"
export NAMESPACE="cma-demo"

oc config delete-context crc 2>/dev/null || true
oc login "$CRC_API_URL" --username kubeadmin --password "$CRC_PASSWORD" --insecure-skip-tls-verify=true
oc config rename-context "$(oc config current-context)" crc

Then source it:

source myenv.sh
Example 2. Verify: context is named crc
oc config get-contexts --context crc
CURRENT   NAME   CLUSTER               AUTHINFO                           NAMESPACE
*         crc    api-crc-testing:6443  kubeadmin/api-crc-testing:6443

3. Enable cluster monitoring and user workload monitoring

~3 minutes (Prometheus and Alertmanager pods take about 2-3 minutes to reach Running)

What: Create the cluster-monitoring-config ConfigMap in the openshift-monitoring namespace with enableUserWorkload: true.

Why: CRC ships with cluster monitoring disabled by default to save memory. The Prometheus trigger in step 03 queries thanos-querier, which only runs when cluster monitoring is active. Setting enableUserWorkload: true in the same ConfigMap also starts the user workload Prometheus instance that scrapes application metrics via ServiceMonitor resources.

oc apply -f - --context crc <<'EOF'
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    enableUserWorkload: true
EOF
configmap/cluster-monitoring-config created

Wait for the monitoring pods to be ready:

oc wait pod \
  -l app.kubernetes.io/name=prometheus \
  -n openshift-monitoring \
  --for=condition=Ready \
  --timeout=300s \
  --context crc
If the wait times out, the host machine may not have enough free RAM. Check crc status and confirm at least 2 GB is free after CRC starts. You can also watch pod status with oc get pods -n openshift-monitoring -w --context crc.
Example 3. Verify: thanos-querier is running
oc get pods -n openshift-monitoring -l app.kubernetes.io/name=thanos-query --context crc
NAME                              READY   STATUS    RESTARTS   AGE
thanos-querier-75f678d47d-abc12   6/6     Running   0          2m

4. Install the Custom Metrics Autoscaler operator

~2 minutes (Subscription created in ~10s, CSV ready in ~90s)

What: Install the Custom Metrics Autoscaler operator from OperatorHub into the openshift-keda namespace, then create a KedaController instance to activate it.

Why: The CMA operator ships the KEDA controller and admission webhook. Without a KedaController CR, the operator installs but does not start the scaler.

4a. Create the operator namespace and install the Subscription

oc apply -f - --context crc <<'EOF'
apiVersion: v1
kind: Namespace
metadata:
  name: openshift-keda
---
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: openshift-keda
  namespace: openshift-keda
spec:
  targetNamespaces:
    - openshift-keda
---
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: openshift-custom-metrics-autoscaler-operator
  namespace: openshift-keda
spec:
  channel: stable
  installPlanApproval: Automatic
  name: openshift-custom-metrics-autoscaler-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
EOF

Wait for the CSV to succeed:

oc wait csv \
  -n openshift-keda \
  -l operators.coreos.com/openshift-custom-metrics-autoscaler-operator.openshift-keda \
  --for=jsonpath='{.status.phase}'=Succeeded \
  --timeout=180s \
  --context crc

4b. Create the KedaController instance

oc apply -f - --context crc <<'EOF'
apiVersion: keda.sh/v1alpha1
kind: KedaController
metadata:
  name: keda
  namespace: openshift-keda
spec:
  watchNamespace: ""
  operator:
    logLevel: info
    logEncoder: console
  metricsServer:
    logLevel: "0"
  serviceAccount: {}
EOF
Example 4. Verify: KEDA controller pods are running
oc get pods -n openshift-keda --context crc
NAME                                                  READY   STATUS    RESTARTS   AGE
keda-admission-webhooks-xxxx                          1/1     Running   0          90s
keda-metrics-apiserver-xxxx                           1/1     Running   0          90s
keda-operator-xxxx                                    1/1     Running   0          90s
custom-metrics-autoscaler-operator-xxxx               1/1     Running   0          2m

5. Create the workshop namespace

What: Apply the namespace manifest for cma-demo.

Why: All workshop resources land in this namespace. A dedicated namespace makes cleanup straightforward and avoids interfering with other workloads on the cluster.

oc apply -f 00-setup/namespace.yaml --context crc
Example 5. Verify: namespace exists
oc get namespace cma-demo --context crc
NAME       STATUS   AGE
cma-demo   Active   10s

6. Clone the workshop repository

What: Clone the repository to get the YAML manifests for each step.

Why: Each step references YAML files in the corresponding step directory. The oc apply -f commands throughout the workshop expect these files to be present locally.

git clone https://github.com/rdiazgav/cma-workshop.git
cd cma-workshop

7. Export workshop variables

What: Source myenv.sh to set the environment variables used throughout the workshop.

Why: The myenv.sh file holds the cluster credentials and context name. Sourcing it once ensures every oc command in subsequent steps uses the crc context without requiring a login prompt.

source myenv.sh
