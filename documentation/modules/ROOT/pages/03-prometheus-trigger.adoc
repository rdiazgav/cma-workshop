= Step 03 - Prometheus Trigger
include::_attributes.adoc[]

This step replaces the CPU trigger from step 02 with a Prometheus trigger that queries CPU usage directly from thanos-querier using cAdvisor metrics already available in the cluster monitoring stack. No additional exporters or ServiceMonitors are required.

== Prerequisites

* xref:02-cpu-trigger.adoc[Step 02] reset: `myboot-cpu-scaler` ScaledObject deleted
* Cluster monitoring and user workload monitoring enabled (xref:00-setup.adoc#cluster-monitoring[step 3 of setup])
* `oc` CLI authenticated as cluster-admin

== How It Works

Thanos-querier is the OpenShift cluster monitoring component that aggregates metrics from both the platform Prometheus and the user workload Prometheus. KEDA queries thanos-querier using a PromQL expression and a bearer token tied to a ServiceAccount that has been granted the `thanos-metrics-reader` Role in the `openshift-monitoring` namespace.

cAdvisor already tracks CPU time for every container in the cluster and exposes it as `container_cpu_usage_seconds_total`. No `ServiceMonitor` or application changes are needed. The PromQL query computes a 2-minute rate and multiplies by 1000 to express the result in millicores. KEDA adds a replica whenever the total CPU usage across all `{app-name}` pods exceeds 50 millicores.

NOTE: OpenShift CRC scrapes cAdvisor every 60 seconds. The Prometheus `rate()` function requires at least two data points within the window to return a value. A `[1m]` window contains only one point at most and returns empty, which KEDA treats as 0 (no scale-up). A `[2m]` window reliably captures two scrape points and is the minimum window for CRC.

NOTE: `myboot` is a Spring Boot 1.5 application that does not expose a Prometheus metrics endpoint. Using cAdvisor CPU metrics lets the workshop demonstrate the full authentication and PromQL path without requiring a custom exporter.

== Steps to Apply

=== 1. Create the ServiceAccount and grant monitoring access

*What:* Create a ServiceAccount in `{namespace}`, create a `thanos-metrics-reader` Role in `openshift-monitoring`, and bind the ServiceAccount to it via a RoleBinding.

*Why:* Thanos-querier requires bearer token authentication. Using a namespaced RoleBinding in `openshift-monitoring` (rather than a cluster-wide ClusterRoleBinding) limits the ServiceAccount's monitoring access to the platform monitoring namespace, following least-privilege.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc apply -f 03-prometheus-trigger/serviceaccount.yaml --context {crc-context}
oc apply -f 03-prometheus-trigger/role.yaml --context {crc-context}
oc apply -f 03-prometheus-trigger/rolebinding.yaml --context {crc-context}
----

[.console-output]
[source,bash]
----

role.rbac.authorization.k8s.io/thanos-metrics-reader created
rolebinding.rbac.authorization.k8s.io/keda-trigger-sa-thanos-metrics-reader created
----

.Verify: RoleBinding is in place

[#triggerauth]
=== 2. Grant keda-operator token permissions and create the TriggerAuthentication

*What:* Grant the `keda-operator` ServiceAccount permission to request bound tokens for `keda-trigger-sa`, then create the `TriggerAuthentication` that uses `boundServiceAccountToken`.

*Why:* With `boundServiceAccountToken`, KEDA requests a fresh, short-lived projected token directly from the Kubernetes TokenRequest API on each metric poll. No manually generated token or Secret is needed. The keda-operator SA needs `create` on `serviceaccounts/token` in this namespace to make that API call.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc apply -f 03-prometheus-trigger/keda-token-role.yaml --context {crc-context}
oc apply -f 03-prometheus-trigger/triggerauth.yaml --context {crc-context}
----

[.console-output]
[source,bash]
----
role.rbac.authorization.k8s.io/keda-operator-token-creator created
rolebinding.rbac.authorization.k8s.io/keda-operator-token-creator created
triggerauthentication.keda.sh/keda-trigger-auth-prometheus created
----

.Verify: TriggerAuthentication uses a bound token (no Secret reference)
[%collapsible]
====
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc get triggerauthentication keda-trigger-auth-prometheus -n {namespace} --context {crc-context} -o yaml
----

[.console-output]
[source,bash]

apiVersion: keda.sh/v1alpha1
kind: TriggerAuthentication

  name: keda-trigger-auth-prometheus
  namespace: cma-demo
spec:
  boundServiceAccountToken:
    - audiences:
        - https://kubernetes.default.svc
      parameter: bearerToken
      serviceAccountName: keda-trigger-sa

[#verify-metric]
=== 3. Verify the cAdvisor metric is available in thanos-querier

*What:* Run a one-shot pod to query thanos-querier and confirm the CPU metric for `{app-name}` returns data.

*Why:* Confirming the metric before applying the `ScaledObject` makes it easier to tell whether a later problem is in the query or in the KEDA configuration.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
CHECK_TOKEN=$(oc create token keda-trigger-sa \
  -n {namespace} --context {crc-context})
oc run metric-check --rm -i --restart=Never \
  --image=registry.access.redhat.com/ubi9/ubi-minimal:latest \
  -n {namespace} --context {crc-context} \
  -- curl -sk \
  -H "Authorization: Bearer $CHECK_TOKEN" \
  'https://thanos-querier.openshift-monitoring.svc.cluster.local:9091/api/v1/query?query=sum(rate(container_cpu_usage_seconds_total%7Bnamespace%3D%22cma-demo%22%2Ccontainer%3D%22myboot%22%7D%5B2m%5D))*1000'
----

NOTE: `CHECK_TOKEN` is a short-lived token generated only to run this verification curl. KEDA itself requests fresh tokens automatically via `boundServiceAccountToken` and never needs this variable.

.Verify: thanos-querier returns a numeric result
[%collapsible]
====
[.console-output]
[source,bash]
----
{"status":"success","data":{"resultType":"vector","result":[{"metric":{},"value":[1728397200,"7.4"]}]}}
----

A numeric value such as `7.4` (millicores at idle) confirms the metric path is working. An empty `result: []` means the pods are too new - wait 2 minutes for cAdvisor to accumulate a full rate window and retry.
====

=== 5. Generate CPU load and observe scaling

icon:clock[] ~6 minutes total (load runs 120 s; metric crosses threshold ~80 s in; pods ready ~140 s in; scale-down completes ~180 s after load stops as the 2-minute rate window drains and the 60-second stabilization window elapses)

*What:* Run the load-generating Job to push total CPU usage above the 50-millicore threshold.

*Why:* The PromQL query uses a 2-minute rate window. Once the window fills with high-CPU samples (~60-90 s into the job), KEDA fires within the next polling interval. Scale-down begins once the rate window drains back below threshold (~120 s after load stops), then the 60-second stabilization window elapses.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc apply -f 02-cpu-trigger/load-job.yaml --context {crc-context}
----

Watch scaling events in a second terminal:

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
watch oc get pods -n {namespace} -l app={app-name} --context {crc-context}
----

.Verify: replica count increased
[%collapsible]
====
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc get scaledobject myboot-prometheus-scaler -n {namespace} --context {crc-context}
----

[.console-output]
[source,bash]

myboot-prometheus-scaler   ...   True    True     False      3m

== What This Solves (Compared to Step 02)

[cols="2,3",options="header"]
|===
| Problem from Step 02 | How This Step Solves It
| Scaling is driven by a built-in CPU trigger that only reads Kubernetes metrics | The Prometheus trigger can evaluate any PromQL expression - CPU, memory, queue depth, or custom business metrics
| No authentication to external metric sources | The TriggerAuthentication pattern works for any token-protected endpoint, not just thanos-querier
|===

== Alternatives Considered

[cols="2,4",options="header"]
|===
| Approach | Notes
| Deploy a standalone Prometheus instance | Works but requires managing a separate installation. Querying thanos-querier reuses the monitoring stack CRC already runs.
| Use `secretTargetRef` with a manually generated token | A ServiceAccount token generated with `oc create token --duration=8h` can be stored in a Secret and referenced via `TriggerAuthentication.spec.secretTargetRef`. This works on all CMA versions but requires regenerating the token before each session. `boundServiceAccountToken` is preferred because KEDA rotates the token automatically. Note: `boundServiceAccountToken` requires a `keda-operator-token-creator` Role in the target namespace granting `create` on `serviceaccounts/token` to the `keda-operator` SA in `openshift-keda`; without it, the bearer token remains empty.
| Use a ClusterRoleBinding with `cluster-monitoring-view` | Works (original approach), but grants the SA cluster-wide monitoring-view access. The `thanos-metrics-reader` RoleBinding in `openshift-monitoring` is narrower.
| Use `rate(...[1m])` for faster scale-up detection | CRC scrapes cAdvisor every 60 seconds. Prometheus `rate()` requires at least two data points inside the window; a `[1m]` window captures only one point and returns empty. KEDA treats an empty result as 0, so scale-up never fires. Use `[2m]` as the minimum window on CRC.
| Use `unsafeSsl: "false"` with a mounted CA cert | Mounting the CA cert is the production-safe approach. The workshop uses `unsafeSsl: "true"` to keep the setup shorter. See the link:https://docs.redhat.com/en/documentation/openshift_container_platform/4.17/html/nodes/automatically-scaling-pods-with-the-custom-metrics-autoscaler-operator[CMA documentation] for the full CA cert setup.
|===

== Reset

Delete resources in reverse order. The `TriggerAuthentication` must be deleted before the Secret it references. The RoleBinding and Role live in `openshift-monitoring`, not `{namespace}`.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc delete scaledobject myboot-prometheus-scaler -n {namespace} --ignore-not-found --context {crc-context}
oc delete triggerauthentication keda-trigger-auth-prometheus -n {namespace} --ignore-not-found --context {crc-context}
oc delete rolebinding keda-operator-token-creator -n {namespace} --ignore-not-found --context {crc-context}
oc delete role keda-operator-token-creator -n {namespace} --ignore-not-found --context {crc-context}
oc delete rolebinding keda-trigger-sa-thanos-metrics-reader -n openshift-monitoring --ignore-not-found --context {crc-context}
oc delete role thanos-metrics-reader -n openshift-monitoring --ignore-not-found --context {crc-context}
oc delete serviceaccount keda-trigger-sa -n {namespace} --ignore-not-found --context {crc-context}
oc delete job myboot-load -n {namespace} --ignore-not-found --context {crc-context}
oc wait --for=condition=available deployment/{app-name} -n {namespace} \
  --timeout=120s --context {crc-context}
----
